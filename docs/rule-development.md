# Rule development contract

A rule must specify its ID/version, required data, measurement definition,
configuration provenance, threshold comparison, severity, evidence confidence,
limitations and likely intentional exceptions before it is advertised.

For `trace_width` version 1:

- Input: normalized straight segments and arcs with explicit width, net and layer.
- Measurement: stored width in millimeters; no current-capacity calculation.
- Condition: `width_mm < minimum_mm`; equality does not trigger.
- Threshold: explicitly supplied by the user; finite and greater than zero.
- Output: warning, deterministic origin, high confidence in the comparison.
- Location: stored start point on the affected track; object ID links full geometry.
- Exceptions: intentionally narrow routing or project-specific requirements; users
  may adjust the threshold. Per-object suppression is not implemented yet.
- Coverage: zones, pads, net-class rules and KiCad custom DRC rules are unassessed.

Tests must cover below/equal/above thresholds, user configuration, units, locations,
identity, negative cases and malformed prerequisites. Geometry rules additionally
need independent numerical expectations and transforms/topology cases. A fixture
generated by the same geometry code being tested is not an independent oracle.

Every finding includes a title, severity, confidence, origin, source object,
measurement and unit, threshold, explanation and possible action. Avoid unsupported
failure predictions. A future missing prerequisite must produce a skip reason;
absence of findings must not conceal that a check could not run.

Before release, evaluate on real boards with human reviewers. Track actionable,
intentional, incorrect and unclear findings separately. Group repeated findings
when useful without discarding individual evidence or affected geometry.
